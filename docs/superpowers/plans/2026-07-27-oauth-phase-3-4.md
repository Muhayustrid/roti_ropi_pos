# OAuth Backend Phase 3–4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete Mobile POS OAuth Phase 3–4 with exact request authorization, role permissions, scoped bootstrap/opening, existing-Customer resolution, and fresh regression evidence.

**Architecture:** Register a focused Frappe `auth_hook` for exact OAuth/API route enforcement, then retain endpoint-level user/role/POS-mode checks. Reuse existing authorization, response, idempotency, and session services; add one customer service and thin API adapter. Existing validated Phase 3–4 implementation in sibling app checkout is source material, but worktree code and tests remain authoritative.

**Tech Stack:** Python 3, Frappe 16, ERPNext 16, Frappe IntegrationTestCase, JSON fixtures, pre-commit.

## Global Constraints

- OAuth Client provisioning stays manual per site; repository stores no Android client secret.
- PKCE challenge must be non-empty and method exactly `S256` for Mobile POS authorize and approve.
- Exact Mobile POS allowlist contains only bootstrap, current/open sessions, and customer search.
- Normal ERPNext permissions remain active; only app-owned idempotency storage may bypass permissions.
- Customer search/resolution never creates or mutates Customer.
- Preserve current untracked Phase 3–4 work; do not commit, push, deploy, or modify original checkout.
